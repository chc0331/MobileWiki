## 1. 목적과 성공의 의미

SLM Wiki는 한국어 메모를 스마트폰 안에서 정리하는 개인 위키 앱이다. 사용자가 남긴 기록을 비슷한 주제끼리 묶고 각 기록에서 요약·개념·날짜를 찾는다. 사용자는 검색과 짧은 질문으로 필요한 원문에 돌아갈 수 있다.

이 POC(Proof of Concept, 실현 가능성을 확인하는 시험)의 목적은 작은 모델이 정한 자원 안에서 도움이 되는 결과를 내는지 판단하는 것이다. 기능이 실행되어도 성공 여부는 9절의 품질·자원·실사용 기준을 모두 확인한 뒤 판정한다.

독자는 앱을 설계·구현하는 개발자와 결과를 평가하는 사용자다. 이 문서는 앱 전체의 요구사항과 검증 방법을 정한다. 먼저 실행하는 PC용 임베딩 학습 실험은 [임베딩 실험 안내](embedding/README.md)에 기록한다. 그 결과만으로 Android 앱의 품질·자원·실사용 합격을 판정하지 않는다.

## 2. 확정 사항과 범위

### 2.1 사용자와 환경

대표 사용자는 육아와 직장을 병행하는 사람이다. 짧은 시간에 메모를 남기며 병원 방문·어린이집 준비물·여행 예약·연차처럼 날짜와 변경 이력이 있는 기록을 자주 찾는다. 모델 이름이나 처리 과정을 몰라도 원문 저장 여부와 정리 상태를 구별할 수 있어야 한다.

| 구분 | 확정 내용 |
| --- | --- |
| 대상 환경 | Android 12 이상, ARM64, RAM 8GB 중급기, CPU 전용 |
| 개발 화면 | Kotlin·Jetpack Compose, 메모·묶음·그래프·검색 하단 탭 4개 |
| 필수 규모 | 원문 메모·가져온 문서 합계 1,000건. 파일 하나를 원문 하나로 계산 |
| 확장 시험 | 5,000건에서 품질·속도·메모리 한계 측정. 필수 합격선과 구분 |
| 입력 | 직접 작성, UTF-8 TXT·Markdown, 텍스트 층이 있는 PDF |
| 모델 개선 | PC용 임베딩 하위 POC에서 텍스트 전용 EmbeddingGemma 2의 미세 조정을 시험. 생성 모델 추가 학습은 제외 |
| 산출물 관리 | 검수된 합성 데이터와 임베딩 학습 모델, 앱용 변환물을 Hugging Face Hub의 비공개 저장소에서 분리해 버전 관리 |
| 실사용 | 본인 1인·7일. 여러 사용자에 대한 적합성은 미확인으로 보고 |
| 설치 | 모델이 포함된 POC 설치본을 직접 설치. 첫 실행 때 모델 다운로드를 요구하지 않음 |

‘중급기’라는 분류와 RAM 수치만으로 실기기 성능을 판단할 수 없다. 1단계 검증을 시작하기 전에 실제 기종·칩셋·OS 빌드를 평가 기록에 고정한다. 특정 기기의 성능은 아직 확인하지 않았다.

PC용 임베딩 하위 POC는 TXT·Markdown의 텍스트 내용만 다룬다. 로컬 Qwen3 모델이 가상 메모를 만들고, EmbeddingGemma 2가 검색과 유사 문서 묶기를 학습한다. 묶음 이름은 원문에 실제로 나온 표현에서 고른다. PDF 추출·Android 변환·앱 실행은 이 하위 POC의 합격 범위에 넣지 않는다.

### 2.2 이번 POC에서 다루지 않는 기능

음성 입력의 AI 처리, OCR(사진에서 글자를 읽는 기술), 이미지 이해, 스캔 PDF 해석, 암호 PDF, PDF 표 구조 복원은 제외한다. 다회차 대화, 외부 지식 검색, 일정 알림·캘린더 연결, 계정·동기화·협업 기능도 제외한다. 약 이름은 원문에서 찾되 복용법·진단을 새로 제안하지 않는다.

다음 입력 상한은 작업량을 통제하기 위한 초기 설계값이다. 제품의 실측 한계로 해석하지 않는다. 상한 변경은 평가 전에 문서 버전과 함께 기록한다.

| 입력 | 상한과 처리 |
| --- | --- |
| 직접 작성·TXT·Markdown | 원문당 20,000자. 초과하면 저장·등록을 거부하고 이유를 알림. 작성 화면의 입력은 유지하며 자동으로 잘라 저장하지 않음 |
| 파일 크기 | 파일당 10MB. MB는 1,000,000바이트 |
| PDF | 파일당 50쪽, 추출 글 합계 100,000자 이하. 어느 상한이든 넘으면 등록 거부 |
| 질문 | 500자 이하, 한 번에 한 질문. 문맥을 이어 가는 채팅 기록은 사용하지 않음 |
| 생성 길이 | 요약·답변은 각각 최대 128 출력 토큰. 토큰은 모델이 글을 나눠 읽고 만드는 단위이며 글자 수와 다름 |

긴 원문은 검색용 조각으로 나누되 원문 전체를 보존한다. 원문 수와 조각 수, 길이 분포를 함께 측정한다. 1,000개의 짧은 메모 성능을 1,000개의 긴 PDF 성능으로 일반화하지 않는다.

## 3. 양보하지 않는 원칙

### 3.1 P1 — 설치 후 모든 기능의 오프라인 동작

최종 설치본에 인터넷 권한이 없어야 한다. 라이브러리 설정까지 합쳐진 Manifest(앱의 권한·구성 파일)를 검사한다. 모델·토크나이저·견본을 설치본에 넣고 신규 설치 후 비행기 모드에서 초기 안내부터 검색·답변까지 확인한다.

Hugging Face Hub는 개발 PC의 모델·데이터 보관과 버전 관리에만 사용한다. 앱은 Hub에 접속하지 않는다. 평가할 파일을 미리 받아 검증한 뒤 설치본에 넣는다. 모델을 앱에서 내려받거나 업데이트하는 기능은 추가하지 않는다.

앱의 직접 통신과 다른 앱의 파일 제공은 구별한다. 파일 가져오기·내보내기는 Android 파일 선택기를 사용한다. 오프라인 시험은 기기에 실제로 저장된 파일로 수행한다. 온라인 파일을 내려받아야 하는 제공자는 오프라인 동작 보장 대상이 아니다.

### 3.2 P2 — 자동 외부 전송 금지, 사용자 내보내기만 예외

원문·임베딩·요약·개념·질문·피드백·진단 로그를 자동으로 밖에 보내지 않는다. 자료는 앱 전용 저장소에 보관한다. 광고·분석·외부 오류 수집 SDK를 넣지 않는다. 자동 백업과 자동 기기 이전에서 앱 데이터를 제외한다. 원문을 담는 운영 로그도 남기지 않는다.

개발 PC에서 Hub에 올리는 데이터는 사람이 만든 가상 메모·평가 항목으로 한정한다. 실제 사용자 메모·가져온 문서·질문·피드백·로그는 Hub 계정과 저장소에 올리지 않는다. 합성 데이터는 기본 비공개 저장소에 두고, 공개 전환은 별도 검토 후 진행한다.

사용자가 직접 실행하는 F12 내보내기는 명시적 예외다. 내보낼 대상과 저장 위치를 선택하고 완료 여부를 확인하게 한다. 파일 선택기의 클라우드 저장소를 고르면 다른 앱이 전송할 수 있음을 짧게 알린다. 앱에 인터넷 권한이 없다는 사실을 내보낸 파일의 외부 전송 차단으로 설명하지 않는다.

자동 백업 설정과 Android 12 이상의 백업·기기 이전 제외 규칙을 함께 적용한다. 지원 기기의 백업·복원·이전 시험으로 확인한다. OS 침해·루팅이나 사용자가 별도로 촬영한 화면까지 막는다고 주장하지 않는다.

### 3.3 P3 — 원문이 뒷받침하는 출력

요약·개념 페이지·질문 답변의 사실 진술에는 원문 근거가 있어야 한다. 출력이 원문에 없거나 원문과 모순되는 사실을 하나 이상 포함하면 ‘사실 오류 출력’으로 센다. 요약과 답변의 오류 출력 비율은 각각 5% 이하여야 한다. 계산과 표본은 9.1절에서 정한다.

읽지 못한 자료를 보충하거나 모호한 날짜를 확정하지 않는다. 약 이름·인명·날짜·금액·부정 표현의 변경은 작아 보여도 사실 오류다. 근거가 없으면 “기록에서 확인할 수 없습니다”라고 답한다. 답할 수 있는 질문도 회피하는 문제는 정답률로 별도 판정한다.

## 5. 기능 요구사항 F1~F14

각 기능은 아래 완료 기준과 9절의 품질 기준을 함께 적용한다. 처리 완료와 평가 합격 여부는 별도로 판정한다.

| ID·기능 | 입력·출력과 처리 시점 | 실패·예외 동작 | 완료 기준 |
| --- | --- | --- | --- |
| F1 메모 작성 | 제목 선택, 본문, 작성 시각 입력 → 원문과 수정 버전 저장. 제목이 없으면 본문 첫 줄로 목록 표시 | 빈 본문·상한 초과 안내. 저장 실패 시 성공 표시 금지, 입력 유지 | 앱 종료·재시작 후 원문 동일. AI 처리 전에도 열람·수정 가능 |
| F2 파일 가져오기 | 로컬 TXT·MD·텍스트 PDF 선택 → 형식·상한 검사 → 추출 미리보기 → 등록. PDF 원본·쪽수·추출 글 보존 | 암호·손상·추출 불가·상한 초과를 구분. 텍스트 없는 페이지는 표시. 혼합 PDF는 부분 처리 확인 후 등록 | 한글·핵심 값·페이지 대응 확인. 취소한 파일은 검색 대상이 되지 않음 |
| F3 저장 직후 처리 | 원문·낱말 색인은 먼저 반영. 임베딩·임시 묶음·날짜 규칙은 UI를 막지 않고 처리 | 대기 중에는 낱말 검색 사용. 실패 작업은 원문을 지우지 않고 재시도 가능 | 처리 전후 원문 접근 가능. 임시 묶음임을 표시하고 최신 버전만 반영 |

## 6. 처리 흐름과 데이터의 기준

### 6.1 필요한 용어와 순서

임베딩(embedding)은 글의 의미를 비교하기 위한 숫자 배열이다. 낱말이 달라도 내용이 가까운 기록을 찾고 묶는 데 쓴다. 생성 모델은 근거 글을 읽고 요약·답변을 만든다. RAG(Retrieval-Augmented Generation)는 먼저 근거를 검색한 뒤 그 근거를 읽혀 답하게 하는 방식이다.

저장된 원문이 모든 파생 결과의 기준이다. 처리 순서는 다음과 같다.

1. 원문과 수정 버전을 저장하고 낱말 색인을 반영한다. 저장 성공을 사용자에게 알린다.
2. 원문을 검색용 조각으로 나누고 임베딩·임시 묶음·날짜 규칙을 계산한다.
3. 백그라운드에서 요약·개념과 원문 근거를 추출한다. 최신 원문 버전인지 확인한 뒤 결과를 반영한다.
4. 24시간 주기 작업에서 변경된 자료의 묶음을 다시 계산한다. OS가 미룬 작업은 앱 재실행 시에도 이어서 처리한다.
5. 개념 페이지는 열 때, 질문 답변은 질문할 때 생성한다. 버전이 같은 개념 페이지는 캐시를 사용한다.

두 모델의 추론은 한 번에 하나씩 수행한다. 질문 답변을 다음 백그라운드 작업보다 우선한다. 진행 중 작업은 안전한 중단 지점에서 멈춘다. 메모리가 부족하면 임베딩 모델을 내린 뒤 생성 모델을 올리는 방식도 비교한다. 모델 교체·대기 시간은 사용자 응답 시간에 포함한다.

정리 작업은 대기·처리 중·완료·실패·취소 상태를 가진다. 자동 재시도는 실패 작업당 최대 2회다. 이후에는 실패 이유와 수동 재시도를 보여 준다. 원문 버전·작업 종류를 기준으로 중복 작업을 합쳐 같은 결과가 여러 번 저장되지 않게 한다.

### 6.2 문서에서 정할 최소 데이터 계약

구현 전에 아래 정보가 저장·조회·내보내기 과정에서 유지되는지 확인한다. 이 PRD는 외부 서버 API를 추가하지 않는다.

| 대상 | 반드시 보존할 정보 |
| --- | --- |
| 원문 | 고유 ID, 원문 종류·본문, 제목, 작성일과 그 출처, 시간대, 등록일, 수정 버전, 견본 여부 |
| 파일·검색 조각 | 원문 ID·버전, 파일 내용 식별값, 원본 파일 위치, PDF 쪽수, 추출 글과 원문 구절의 위치 |
| AI 결과 | 원문 ID·버전, 모델·변환물·프롬프트 버전, 생성 시각, 처리 상태, 출력과 근거 목록 |

질문 답변의 근거에는 원문을 사용한다. 생성한 요약이나 개념 페이지를 다시 사실 근거로 쓰는 순환을 피한다. 메모를 수정하면 그 메모에 의존한 답변 캐시도 폐기한다. 별도 대화 기록은 저장하지 않으며 피드백을 남긴 결과만 원문 버전과 연결해 보관한다.

긴 문서의 요약은 모든 조각에서 핵심 원문 구절을 추린 뒤 그 구절을 모아 생성한다. 각 호출의 문맥 상한을 지키며 이 처리 비용도 초기 정리 시간에 포함한다. 모든 조각을 처리해야 문서 전체 요약으로 표시한다. 일부 조각 처리에 실패하면 요약을 미완료로 남긴다. 개념 페이지도 사용한 원문 목록과 처리 범위를 표시한다. 요약에 필요한 근거가 문맥 상한에 들어가지 않으면 부분 요약임을 알리고 전체 요약 완료로 세지 않는다.

임베딩이 가깝다는 이유만으로 다른 아이·병원·행사를 같은 개념으로 합치지 않는다. 별칭 합치기는 원문 근거가 있는 후보로 제시하고 사용자가 확정한다. 묶음 분리·이동과 별칭 정정은 자동 재처리보다 우선한다.

### 6.3 파일 복원과 삭제의 경계

내보내기에는 임베딩·검색 색인·실행용 요약·답변 캐시를 넣지 않는다. 피드백의 의미가 보존되도록 당시 질문·출력·근거 ID·원문 버전·모델·프롬프트 버전을 이력에 함께 보관한다. 이 이력은 검색 근거나 현재 AI 결과로 쓰지 않는다. 가져올 때는 원문과 사용자 정정을 복원하고 실행용 파생 결과를 다시 계산한다. 모델 버전이 달라도 원문을 복원할 수 있어야 한다. 내보내기는 사용자가 선택해 실행하며 주기적 백업 기능으로 확장하지 않는다.

보관 파일에는 평문 자료가 들어가며 별도 암호화는 보장하지 않는다. 저장 전에 이 사실과 포함 대상을 알린다. ZIP 안의 경로가 앱 저장소 밖을 가리키지 않는지, 파일 목록과 내용 식별값이 일치하는지 검사한다. 가져오기에 실패하면 등록 전 임시 파일을 정리한다. 전체 묶음을 검사한 뒤 등록한다.

같은 ID에 내용이 다른 항목이 들어오면 기존 원문을 보존하고 새 ID로 사본을 만든다. 보관 파일의 연결 정보도 새 ID로 바꾼다. 피드백은 과거 결과에 대한 기록으로 복원한다. 재생성 결과의 평가로 옮기지 않는다.

앱에서 삭제한 데이터가 앱 안에 다시 나타나면 실패다. 앱은 사용자가 이전에 내보낸 파일까지 찾아 삭제하지 않는다. 이전 보관 파일을 사용자가 다시 가져오면 그 안의 기록이 복원된다고 안내한다. 저장장치에서 물리적으로 복구할 수 없다고 보장하지 않는다.

## 7. 모델·실행 도구 비교

### 7.1 채택 원칙

앱에는 임베딩 모델 1개와 생성 모델 1개를 넣는다. 생성 모델은 우선 5억~15억 파라미터의 4비트 후보를 비교한다. 파라미터는 모델이 학습한 숫자다. 4비트는 그 숫자를 작게 저장하는 방식이다. 숫자 개수와 파일 크기만으로 한국어 품질이나 실행 메모리를 예측하지 않는다.

임베딩 100~300MB는 초기 탐색 범위다. 후보마다 변환 결과가 다르므로 필수 상한은 두 모델에 실제로 필요한 파일의 합계 1GB다. 토크나이저·설정·필수 어댑터·중복 가중치도 합계에 포함한다. 앱 코드·런타임·원문·색인은 별도로 기록한다.

모델은 정확한 ID와 변환물의 내용 식별값을 기록한다. 문서에 ‘지원’이라고 적으려면 모델 카드의 언어 지원, 런타임이 지원하는지, 실기기 실행을 확인했는지를 구분해야 한다. 라이선스의 이용·수정·앱 동봉·재배포 조건도 각각 확인해 기록한다.

### 7.2 초기 비교 순서

| 순서 | 후보와 목적 | 진행 조건 |
| --- | --- | --- |
| 1 | `google/gemma-3-1b-it` + `google/embeddinggemma-2`의 텍스트용 변환물. LiteRT-LM CPU 통합 기준선 | Android CPU 변환물·라이선스·1GB 상한부터 확인 |
| 2 | `Qwen/Qwen3-0.6B` + 같은 임베딩. 작은 생성 모델과 비교 | non-thinking 모드, 같은 입력·출력 예산. LiteRT-LM 메모리 실패 시 같은 모델의 llama.cpp 경로 비교 |
| 3 | `intfloat/multilingual-e5-small` ONNX 변환물을 임베딩 대안으로 비교 | Android ARM CPU에서 검증. x86용 최적화 파일이 그대로 사용 가능하다고 전제하지 않음 |
| 예비 | `intfloat/multilingual-e5-base`, `google/embeddinggemma-300m`, `Snowflake/snowflake-arctic-embed-m-v2.0`, `Qwen/Qwen3.5-0.8B`, `LiquidAI/LFM2.5-1.2B-Instruct` | 앞 조합의 실패 원인을 해결할 근거가 있을 때만 추가. 모든 조합의 전수 실험은 하지 않음 |

EmbeddingGemma 300M과 2는 별도 모델이며 구분해서 기록한다. 모델별 확인 근거는 [검증 근거 2절](검증_근거.md#2-모델-후보의-정확한-구분)에서 관리한다. 최종 채택 모델은 아직 없다.

생성은 LiteRT-LM을 우선한다. llama.cpp는 후보 변환물이나 메모리 조건 때문에 필요한 경우의 대안이다. 임베딩은 해당 모델을 지원하는 LiteRT 계열 또는 ONNX Runtime을 비교한다. 실제로 쓰지 않는 런타임까지 앱에 동봉하지 않는다.

Kanana-2와 HyperCLOVA X SEED는 PC의 합성 자료 비교 평가에서만 사용한다. 앱 탑재 가능 여부는 모델별 정확한 ID와 라이선스·재배포 조건을 확인해 판단한다. 비교 모델의 출력은 정답이나 학습 데이터에 자동 편입하지 않는다.

### 7.3 모델·데이터 산출물 관리

Hugging Face Hub를 모델과 데이터 저장소의 기준으로 사용한다. GitHub에는 코드와 이 PRD를 두고 Hub에는 데이터셋 저장소와 모델 저장소를 분리해 둔다. PC용 임베딩 하위 POC의 학습 산출물도 이 원칙을 따른다. Hub를 선택한 이유와 버전 고정 방법은 [검증 근거 8절](검증_근거.md#8-hugging-face-hub-운영-원칙)에 정리한다.

평가 데이터 저장소에는 합성 데이터와 데이터 설명서만 올린다. 개발·평가 분할, 검수 상태, 생성기·프롬프트 버전, 데이터 파일 해시를 기록한다. 평가 실행마다 데이터셋 ID와 전체 commit SHA(특정 저장소 버전을 가리키는 전체 식별값)를 고정한다. 같은 변경 가능한 최신 버전을 가리키는 `main`만 기록하지 않는다.

모델 저장소에는 임베딩 학습 어댑터나 직접 변환한 모델 파일, 토크나이저, 실행 설정과 설명서를 둔다. 원본 모델 ID와 전체 commit SHA, 학습·변환·양자화 도구 버전, 설정, 파일 해시, 라이선스, 평가 결과를 함께 기록한다. 라이선스가 앱 내장·재배포를 허용하지 않는 모델 파일은 업로드하지 않는다. 원본 후보는 원 제작자 Hub 저장소의 ID와 고정 revision으로 참조한다.

임베딩 하위 POC는 학습·개발·고정 평가 분할을 한 데이터셋 저장소 안에서 구분한다. 모델 설명서에는 기반 모델 ID와 revision, 데이터셋 ID와 revision, 학습 설정, 평가 결과를 기록한다. 가족·사건 단위로 분할이 섞이지 않았는지 확인한다. 생성 모델의 학습과 공개 배포는 이 단계의 합격 조건이 아니다.

데이터·모델 저장소는 기본 비공개로 만든다. 공개는 개인정보·라이선스·데이터 출처를 사람이 확인한 뒤 진행한다. Hub 인증은 개발용 PC에서만 사용한다. 저장소별 최소 권한 토큰을 쓰고 토큰을 GitHub, 코드, 앱, 평가 로그에 넣지 않는다. 평가 앱은 Hub 토큰이나 Hub 클라이언트를 포함하지 않는다.

| Hub 관리 항목 | 필수 기록·확인 |
| --- | --- |
| 데이터셋 저장소 | 합성 여부, 스키마, 개발·평가 분할, 생성기·프롬프트, 검수 상태, 데이터 해시, commit SHA |
| 모델 저장소 | 원본 모델 ID·revision, 라이선스, 변환·양자화 도구와 설정, 토크나이저, 파일 해시, 평가 결과, commit SHA |
| 각 평가 실행 | 데이터셋 저장소 ID·SHA, 모델 저장소 ID·SHA, 앱 빌드, 런타임, 측정 설정 |
| 접근 제어 | 비공개 기본값, 저장소별 최소 권한 토큰, 비밀 값 미등록, 공개 전 사람 검토 |

## 8. 합성 평가 데이터

### 8.1 생성 목적과 도구

PC용 임베딩 하위 POC는 로컬 Qwen3 8B 4비트 모델로 가상의 메모·검색 질문을 만든다. 모델이 메모 초안을 만들고 사건 카드의 정답 관계를 학습 자료로 바꾸는 과정을 여기서는 데이터 증류라고 부른다. 교사 모델의 내부 점수나 가중치를 복제하는 방식은 아니다. 8B 모델이 M2에서 실행되지 않거나 예비 생성 속도로 12시간 생성 한도를 넘을 것으로 보이면 4B 4비트 모델로 바꾸고 최종 자료를 처음부터 만든다. 두 교사 모델의 출력은 한 데이터셋에 섞지 않는다.

사건 카드에는 가상의 가족·날짜·주제·확인할 사실을 먼저 적는다. Qwen은 사건마다 메모 4개와 질문 1개를 작성한다. 찾을 사실은 첫 메모에만 두고 다른 메모는 같은 사건의 준비·후속 기록으로 만든다. 코드는 근거 문장이 실제 메모에 있는지, 질문에 답이 노출되지 않았는지, 문서 길이와 날짜 형식이 맞는지 검사한다. 생성 결과를 바로 정답으로 믿지 않는다. 답을 뒷받침할 수 없는 항목은 고치거나 제외하고 이유를 남긴다.

검색 질문의 절반은 원문과 다른 표현을 쓰도록 사건 유형별 문장으로 바꾼다. 사건 카드의 가상 인물 이름을 메모 제목과 질문에 반영하되 날짜를 질문에 일률적으로 덧붙이지 않는다. Qwen이 다른 메모에 정답을 반복하면 그 문장을 제거하고 수정 사실을 기록한다. 고정 평가 자료를 잠그기 전에 이 문장들이 여전히 자연스럽고 정답 문서가 하나인지 원문과 대조한다.

실제 메모·가져온 파일·개인 질문은 생성 입력에 사용하지 않는다. 모델 다운로드와 비공개 Hub 업로드는 개발 PC에서만 수행한다. 합성 자료 생성·학습·평가 도중에는 외부 생성 API를 호출하지 않는다. 앱의 오프라인 원칙과 개발 PC의 모델 관리 작업을 구분한다.

검수를 마친 합성 자료만 7.3절에 정한 Hugging Face Hub 데이터셋 저장소에 올린다. 저장소는 비공개로 유지하고 전체 commit SHA를 평가 기록에 남긴다. 사람이 원문과 정답을 대조하기 전의 점수는 잠정 결과로 표시한다. 실제 사용자 자료가 섞이지 않았는지 업로드 전에 확인한다.

### 8.2 데이터 구성과 정답 검수

임베딩 하위 POC는 텍스트 원문 800건을 학습용, 300건을 개발용, 1,000건을 고정 평가용으로 만든다. 같은 가족·사건의 다른 메모는 한 분할에만 넣는다. 고정 평가 자료에는 근거가 있는 검색 질문 140개와 관련·무관 문서 쌍 100개를 둔다. 검색은 상위 5개 원문에 근거가 있는지 확인하고 첫 결과가 근거 문서인지도 보조로 기록한다. 묶음은 9.1절의 문서 쌍 F1으로 평가한다. 개발 자료로 군집 기준값과 묶음 이름 추출 규칙을 정한 뒤 고정 평가 자료는 변경하지 않는다. 데이터 생성·학습 실행의 총시간 상한은 24시간이다.

아래의 앱 전체 평가 자료는 임베딩 하위 POC의 텍스트 전용 자료와 별개다. 개발용 원문 300건과 최종 평가용 원문 1,000건을 별도로 만든다. 최종 평가 자료는 가족·사건 단위로 개발용 자료와 겹치지 않게 나눈다. 같은 사건을 다른 문장으로 바꾼 자료도 같은 쪽에 넣는다. 최종 평가 자료로 프롬프트를 고쳤다면 그 자료는 개발용으로 전환하고 새 평가 자료를 만든다.

최종 1,000건은 직접 작성·TXT·MD 상당의 메모 900건과 텍스트 PDF 100건으로 구성한다. 메모는 800건이 50~500자, 100건이 501~20,000자 범위다. PDF는 80건이 1~5쪽, 20건이 6~50쪽 범위다. 실제 길이·쪽수·검색 조각 수를 기록하며 2.2절의 상한 사례도 포함한다.

| 평가 자료 | 구성 |
| --- | --- |
| 요약 200건 | 메모·문서 요약 150건과 개념 페이지 50건. 사람이 핵심 정보·근거·금지 추론을 표시 |
| 질문 답변 200건 | 답변 가능 140건, 근거 없음 40건, 해결할 근거가 없는 상충 기록 20건 |
| 날짜 100건 | 명확한 날짜 40건, 기준일 있는 상대 날짜 30건, 기준 불명·여러 해석 30건 |
| 개념·묶음 | 원문 100건의 개념 정답·허용 별칭, 관련/무관 메모 쌍 100쌍. 여러 주제 메모와 미분류 사례 포함 |
| 기능 예외 | 오탈자·동명이인·변경·취소·중복·손상 PDF·스캔 전용 PDF·문서 속 지시문 포함 |

각 평가 항목에는 ID, 데이터 분할, 원문 ID·버전, 질문 또는 작업, 기대 답·핵심 정보, 근거 구절·페이지, 날짜 기준, 답변 보류 이유, 생성 도구·프롬프트 버전, 사람 검수 상태를 남긴다. 자동 생성 정답은 사람이 원문과 대조하기 전에는 평가에 사용하지 않는다. 판단이 어려운 항목은 정답을 고치거나 제외하고 사유를 기록한다.

로컬 Qwen에는 JSON Schema로 구조를 지정한다. 사건별 원시 출력과 학습·개발·평가 JSONL을 구분해 저장하고 형식 오류·중복·누락 근거를 검사한다. 자동 생성 개수, 규칙으로 고친 개수, 사람 검수 통과 개수와 제외 사유를 함께 기록한다. 모델이 채점한 점수는 보조 자료이며 최종 사실 오류 판정은 원문 대조로 한다.

## 9. 평가 방법과 판정

### 9.1 품질 평가

아래 수치는 실제 측정값이 아닌 초기 합격 목표다. 평가 전에 데이터·모델·프롬프트·검색 설정을 고정한다. 기준선은 같은 자료에 대한 낱말 검색만의 결과다. 생성 결과는 원문을 읽고 수작업으로 확인한 정답과 비교한다.

| 지표 | 계산·확인 방법 | 가능 목표 |
| --- | --- | --- |
| P3 요약 사실 오류율 | 사실 오류가 하나 이상 있는 출력 수 ÷ 요약 200건. 문서 요약·개념 페이지도 각각 보고 | 전체 및 각 종류 5% 이하 |
| P3 답변 사실 오류율 | 사실 오류가 하나 이상 있는 출력 수 ÷ 질문 답변 200건 | 5% 이하 |
| 요약 유용성 | 핵심 정보 보존·사실 오류 없음·읽을 수 있는 완성 출력을 모두 만족한 건수 ÷ 해당 종류의 전체 건수 | 문서 요약·개념 페이지 각각 85% 이상 |
| 검색 근거 포함률 | 답변 가능한 140개 질문의 상위 5개 원문 결과를 확인. 정답 근거가 하나 이상 있는 질문의 비율 | 90% 이상 |
| 질문 정답률 | 필요한 답과 유효한 출처를 모두 제시한 질문 수 ÷ 답변 가능한 140건 | 85% 이상 |
| 답변 보류율 | 근거 없음 또는 상충을 정확히 알린 건수 ÷ 해당 유형 전체 | 근거 없음 40건·상충 20건 각각 90% 이상 |
| 날짜 | 확정한 날짜의 정확도, 확정 가능 70건의 정답 추출률, 미확정 대상 30건의 보류율 | 각각 95%·90%·90% 이상 |
| 개념 | 추출한 개념 중 원문 근거·동일 대상이 맞는 비율. 100건별 정답 개념을 하나 이상 찾은 비율도 확인 | 각각 90%·85% 이상 |
| 묶음 | 관련/무관 50쌍씩 평가. 같은 묶음의 정밀도와 관련 쌍을 함께 묶은 재현율의 조화평균인 F1 계산 | 0.80 이상 |

묶음의 정밀도 P는 같은 묶음으로 배치한 쌍 중 실제 관련 쌍의 비율이다. 재현율 R은 실제 관련 쌍 중 같은 묶음으로 배치한 쌍의 비율이다. F1은 `2 × P × R / (P + R)`로 계산한다. 함께 묶은 쌍이 없으면 P를 0으로 둔다. P와 R이 모두 0이면 F1도 0이다.

분모는 시험 전에 고정한다. 빈 출력·실패·불필요한 거절은 사실을 지어낸 것이 아니면 P3 분자에 억지로 넣지 않지만 요약 유용성·질문 정답률에는 실패로 포함한다. 모든 질문에 답변을 거절해 P3만 통과할 수 없도록 한다. 전혀 확정한 날짜나 추출한 개념이 없으면 해당 정밀도는 ‘계산 불가’이며 합격 처리하지 않는다.

결과마다 오류 문장과 근거 구절을 남긴다. 출력 단위 오류율 외에 주장 단위 오류도 보조로 기록한다. 표본 수·관측 비율·95% Wilson 신뢰구간을 함께 보고한다. 관측 오류율이 5% 이하여도 실제 모든 사용에서 5% 이하라고 입증한 것은 아니다. 합격 판정은 이 POC의 고정 평가 자료에 대한 결과다.

PDF 오류는 두 단계로 기록한다. 먼저 추출 글과 PDF 화면을 비교해 누락·순서·값 오류를 찾는다. 다음으로 생성 결과와 추출 글을 대조한다. 사용자가 보는 최종 답이 원본 PDF와 다르면 종단 간 오류율에 포함한다. PDF에서 글을 잘못 추출하고 모델이 그 글을 그대로 읽었다면 추출 오류다. 올바르게 추출한 글에 없는 내용을 모델이 만들었다면 생성 오류다. 주 합격선은 원본 기준의 종단 간 결과에 적용한다.

### 9.2 자원·속도 평가

GB는 1,000,000,000바이트다. 추가 메모리는 같은 데이터·화면에서 두 모델이 내려간 상태를 기준으로 한다. PSS는 공유 메모리를 나눠 계산한 프로세스의 RAM 부담이다. 앱과 별도 추론 프로세스가 있다면 모두 합산한다. Native 메모리와 생성 중의 KV 캐시(앞선 토큰 계산을 보관하는 메모리)도 포함한다.

| 지표 | 측정 조건·목표 |
| --- | --- |
| 모델 파일 | 실제 설치되는 모델 2개의 필수 파일 합계 1GB 이하. 압축 다운로드 크기로 대신하지 않음 |
| 메모리 | 시나리오 실행 중 최대 PSS 증가량 1.5GB 이하. 기준 PSS·전체 최대 PSS·측정 간격도 기록 |
| 저장 | 본문 저장 요청부터 원문·낱말 색인 저장 확인까지 p95 300ms 이하. 파일 추출 시간과 구분 |
| 검색 | 검색 요청부터 상위 원문 결과 표시까지 p95 2초 이하 |
| 답변 | 질문 제출부터 출처와 완성 답변 표시까지 p95 20초 이하. 검색·대기·모델 로딩·교체 포함 |
| 백그라운드 | 단일 메모 처리와 초기 1,000건 정리의 완료 시간·처리량·실패 수 기록. 앱이 대기 상태를 숨기지 않음 |
| 발열·배터리 | 같은 밝기·전원 조건으로 30분 반복 시험. 시작·종료 배터리, 발열 상태, 시간대별 속도 저하 기록 |
| 안정성 | 30분 반복 사용 및 최대 허용 입력 처리에서 비정상 종료·ANR·데이터 손실 0건. ANR은 앱이 반응하지 않는 상태 |

CPU 전용 설정을 실행 기록으로 확인한다. 생성 입력의 전체 문맥은 최대 2,048토큰, 출력은 최대 128토큰을 초기 공통 조건으로 사용한다. 시스템 지시·질문·근거가 문맥을 넘으면 근거 조각 수를 줄이고 원문 위치는 보존한다. 이 범위에서 답할 근거가 부족하면 보류한다. 모델별 입력 형식은 공식 지침을 따르고 차이를 기록한다.

검색·답변은 모델 미로딩 상태 30회와 재사용 상태 100회를 각각 측정한다. 각 집단에서 p95를 계산하며 둘 다 목표를 적용한다. 정렬한 N개 관측값 중 올림(0.95×N)번째 값을 사용한다. 최초 실행이 느리다는 이유로 로딩 시간을 제외하지 않는다. 요청이 60초 안에 끝나지 않으면 시간 초과로 처리하고 검색 결과·원문을 유지한다. 실패·앱 자체 취소·시간 초과 요청은 지연 판정에서 무한대로 계산한다. 성공한 요청만으로 합격 판정을 내리지 않는다. 사용자 취소 동작은 별도 기능 시험에서 확인하며 지연 시험 중에는 수행하지 않는다.

저장 시험은 고정한 본문 100건을 각각 한 번씩 저장한다. 50~500자 60건, 501~5,000자 30건, 5,001~20,000자 10건으로 구성한다. 검색·답변과 마찬가지로 실패 요청을 지연 계산에서 제외하지 않는다. 같은 초기 데이터로 되돌려 다른 모델 조합을 비교한다.

측정에는 실제 기기·칩셋·OS·앱 빌드·CPU 스레드 수·런타임·모델 파일 식별값·양자화 방식·프롬프트·원문 수·조각 수·입출력 토큰 수를 남긴다. 정해진 시나리오를 같은 순서로 반복하고 발열 후 결과와 초기 결과를 구분한다.

### 9.4 본인 1인·7일 사용

매일 실제로 쓸 수 있는 메모를 남기고 필요한 기록을 찾는다. 개인 원문은 기기에 둔다. 측정표에는 성공 여부·소요 시간·오류 유형·피드백만 기록하고 외부 평가 도구에 원문을 보내지 않는다.

7일 동안 S1~S10을 각각 한 번 이상 수행한다. S1~S6의 기록 찾기 과제는 낱말 검색 기준선과 앱 결과에서 근거를 확인하기까지 걸린 시간을 비교한다. S7~S10의 묶음·그래프·수정·삭제·복원·피드백 과제는 해당 동작의 완료 여부·소요 시간·오류를 기록한다. 올바른 원문 도달 여부, 수정 횟수, 불필요한 거절, 기다리다 포기한 횟수도 남긴다. 한 번 시도해 불편했던 기록을 성공한 재시도로 덮어쓰지 않는다.

시나리오 성공은 4절의 기대 결과와 관련 기능 완료 기준을 충족한 경우다. 10개 중 8개 이상 성공하고 데이터 손실이 없어야 한다. 개인정보·삭제·복원 같은 필수 기능 실패는 나머지 성공 건수로 상쇄하지 않는다. 본인 1인의 결과이므로 페르소나 전체에 대한 사용성 검증으로 보고하지 않는다.

### 9.5 최종 판정 규칙

평가 상태와 최종 결과는 별도로 기록한다. 필요한 시험을 실행하지 않았거나 비교 가능한 기록이 없으면 ‘미판정’이다. 완료한 일부 시험의 통과·실패는 함께 기록한다.

| 결과 | 적용 조건 |
| --- | --- |
| 가능 | P1~P3, 모델·메모리 상한, F1~F14 필수 완료 기준, 9.1~9.4절의 합격 목표 모두 충족 |
| 조건부 가능 | P1~P3·모델·메모리·필수 기능·검색 및 답변 품질·날짜·개념 기준은 충족. 아래 허용 범위의 속도·묶음·실사용 항목만 미달 |
| 불가능 | 정한 비교·개선 단계를 마쳤지만 절대 원칙·자원·필수 기준이 미달하거나 조건부 허용 범위에도 들지 못함 |

조건부 가능의 허용 범위는 검색 p95 2초 초과~3초 이하, 답변 p95 20초 초과~30초 이하, 묶음 F1 0.70 이상~0.80 미만, S1~S10 성공 7개다. 해당 항목 외에는 가능 기준을 충족해야 한다. 저장 p95 300ms 초과는 500ms 이하인 경우만 조건부로 허용한다. 여러 항목이 미달하면 모두 기록한다.

조건부 판정에는 현재 가능한 사용 범위, 실패 사례, 개선할 항목과 재평가 시험을 반드시 붙인다. P3가 5%를 넘거나 메모리가 1.5GB를 넘는 경우를 ‘조금 느림’ 같은 조건으로 통과시키지 않는다. 데이터 손실·자동 전송·삭제 자료 부활도 조건부 판정으로 허용하지 않는다.

‘불가능’ 판정은 이 문서에서 정한 기기·후보·자원·입력 범위에만 적용한다. 다른 SLM이나 모든 스마트폰에 일반화하지 않는다. 다른 기준 기기에서 통과한 결과는 원래 기기의 통과로 바꾸지 않고 별도 실험으로 기록한다.

## 10. 실행 단계와 결과 기록

일정을 임의의 날짜로 확정하지 않는다. 아래 표는 Android 앱 전체의 실행 단계다. PC용 임베딩 하위 POC는 이 표에 앞서 별도로 실행하며, 그 결과를 앱 전체의 합격 판정으로 바꾸지 않는다. 아래 진입·완료 조건을 순서대로 적용하고 자료·도구 준비 여부에 따라 실제 소요 시간을 기록한다.

| 단계 | 진입 조건 | 수행 내용 | 완료·중단 기준 |
| --- | --- | --- | --- |
| 1 환경·자원 확인 | 실제 기준 기기, 모델 이용 조건, 비공개 Hub 저장소 접근 준비 | 모델 로딩·짧은 생성·임베딩, API 31 PDF 추출, 오프라인·백업 경로 시험 | 1GB·1.5GB 상한과 최소 실행 가능성 확인. Hub 토큰이 앱에 포함되지 않는 것도 확인 |
| 2 데이터·기준선 | 합성 자료 생성 경로·스키마·비공개 Hub 저장소 준비 | 개발용 자료 검수, 낱말 검색 기준선, 최종 평가 자료 분리·사람 검수. 검수된 합성 데이터와 설명서를 Hub에 올리고 다시 받아 비교 | 데이터 revision SHA·파일 해시·분할·검수 상태 기록. 실제 개인 자료 전송 없음 |

초기 조합 2개를 먼저 평가한다. 실패 원인을 확인한 뒤 예비 후보를 최대 2개 조합까지 추가한다. 임베딩 학습은 별도 하위 POC에서 고정하고, 앱 단계에서는 프롬프트·검색·실행 설정을 최대 2회 개선한다. 예산을 더 쓰려면 별도 후속 실험으로 기록한다. 평가 자료에 맞춰 변경한 내용은 새 평가 자료에서 다시 검증한다.

결과 보고에는 실행 ID, 문서 버전, 평가 기기·빌드, 데이터셋 Hub ID·전체 revision SHA·파일 해시, 모델 Hub ID·전체 revision SHA·파일 해시, 지표별 분자·분모·관측값, 실패 사례, 근거, 최종 판정을 담는다. Hub를 사용할 수 없거나 고정 revision으로 자료를 다시 받을 수 없으면 재현성 시험은 미완료다. 데이터와 실행 환경이 없는 숫자를 결과 표에 채우지 않는다. 현재 모든 실행·성능·실사용 결과는 미판정이다.

## 11. 문서 검수 기준

S1~S10의 기대 결과가 F1~F14와 평가 항목으로 연결되는지 확인한다. 원칙·수치·단위·입력 상한·예외 처리·내보내기 범위는 요약과 본문에서 같은 뜻이어야 한다. 공식 자료로 확인한 사실과 이 POC가 선택한 목표를 구분한다.

내용 검수 뒤 `humanize-korean`으로 표현을 다듬는다. 전문 용어·숫자·조건·한계는 보존한다. 이 자료는 제품 요구사항 문서이므로 교재용 연습문제·정답·학습 이정표와 PDF를 기계적으로 붙이지 않는다. 소스·근거의 내부 링크를 확인하고 모든 작업 파일은 `poc/` 안에서 관리한다.

문서가 읽기 쉬운지 검토한 결과를 실제 사용자의 이해도 시험으로 표현하지 않는다. PC에서 수행한 모델 다운로드·예비 추론·학습과 아직 수행하지 않은 전체 데이터 평가·실기기 시험을 구분해 결과에 남긴다.
